# Project Conventions

> **Status:** Approved by the human on 2026-10-26.

## Purpose

This document defines the style, organization, and development practices that every change in
the project must follow.

The goal is consistency, maintainability, and making the codebase easy for any developer to
understand quickly.

These conventions apply to new code and to modifications of existing code when relevant.

---

# General code principles

## Clarity over brevity

Code must prioritize:

* readability;
* descriptive names;
* clear structure;
* obvious intent.

Do not write overly compact code if it reduces understanding.

---

## Single responsibility

Each file, function, class, or component must have one clear responsibility.

Avoid:

* giant files;
* functions with too many tasks;
* components mixing business logic and presentation.

---

## Reuse

Before creating new logic:

Check whether a similar implementation already exists.

Avoid:

* duplicated code;
* parallel solutions;
* repeated validation.

Do not abstract code that is still changing or has no proven reuse.

---

## Explicit types

PHP application and test files use:

* `declare(strict_types=1);`
* parameter types;
* return types;
* property types where practical;
* PHPDoc only when it adds information that the type system cannot express.

Avoid untyped arrays whose shape is not obvious; document the shape when necessary.

---

# Naming conventions

## Variables

Use:

```text
camelCase
```

Example:

```php
$bookValue
$userProfile
$validatedData
```

Avoid:

```text
$book_value
$BOOK_VALUE
```

---

## Functions and methods

Use names that indicate an action.

Example:

```text
createBook()
calculateTotal()
revokeCurrentToken()
```

Avoid ambiguous names:

```text
process()
handle()
data()
```

without context.

---

## Classes

Use:

```text
PascalCase
```

Example:

```text
BookController
StoreBookRequest
BookResource
AuthService
BookService
```

---

## Constants and enum cases

Use:

```text
UPPER_SNAKE_CASE
```

Example:

```text
MAX_PAGE_SIZE
DEFAULT_TOKEN_TTL
```

---

## Database

* Tables: plural `snake_case` (`users`, `books`).
* Columns: `snake_case` (`user_id`, `created_at`).
* Foreign keys: `<singular>_id` (`user_id`).
* Indexes: descriptive names generated by Laravel unless a custom name is clearer.

---

## Routes and JSON

* Routes: plural resource names under the version prefix (`/api/v1/books`).
* JSON fields: `snake_case` (`created_at`, `updated_at`).
* Response root keys: `data`, `meta`, `links`, `message`, `errors`.
* No abbreviations except standard ones (`id`, `isbn`).

# File organization

The structure must follow the architecture defined in `architecture.md` and Laravel's
conventions.

Avoid:

* placing files without a clear responsibility;
* creating generic folders without need;
* introducing a custom `src/modules` structure.

Project structure:

```text
app/
├── Http/
│   ├── Controllers/Api/V1/
│   ├── Middleware/
│   ├── Requests/
│   └── Resources/
├── Models/
├── Policies/        (only if introduced)
├── Services/        (one per business controller)
└── Providers/

routes/api.php
database/{factories,migrations,seeders}
tests/{Feature,Unit}
```

---

# Feature organization

When the project allows it, prefer capability-oriented organization.

For this project:

* `Auth` behavior lives in `AuthController`, `AuthService`, auth Form Requests, and the
  `User` model.
* `Books` behavior lives in `BookController`, `BookService`, book Form Requests,
  `BookResource`, and the `Book` model.
* Shared HTTP behavior lives in middleware/exception handling, not in either business module.

Do not invent a custom module framework. Laravel's structure is the boundary.

This keeps growth and maintenance manageable without premature modularization.

# Business logic

Important business logic must be separated from:

* routes;
* controllers' HTTP concerns;
* resources/presentation;
* infrastructure.

Correct flow:

```text
Route
  ↓
Form Request (validation)
  ↓
Controller (HTTP only: delegate and respond)
  ↓
Service (business rules, ownership, transactions)
  ↓
Model / query
  ↓
Persistence
```

Incorrect:

```text
Route
  ├── validates
  ├── queries the database
  ├── applies business rules
  └── formats the response
```

Rules:

* Controllers translate HTTP and delegate; they do not query the database or accumulate business
  rules.
* Validation belongs in Form Requests.
* Services are the business-logic layer: one service per business controller (`AuthService`,
  `BookService`).
* Services own ownership, transactions, and token operations. They return models, paginators, or
  arrays, never HTTP responses, and they do not accept HTTP `Request` objects.
* Ownership belongs inside the service: use the authenticated user's `books()` relationship.
* Do not add a repository layer.
* Do not use Actions as a parallel pattern; add or extend a service method instead.

# Error handling

Errors must:

* be explicit;
* have clear messages;
* keep enough context in logs;
* be logged when necessary.

Avoid:

* empty `catch` blocks;
* exposing technical errors to API clients;
* hiding failures;
* returning HTML for API errors.

API errors follow the JSON envelope:

```json
{ "message": "The given data was invalid.", "errors": { "isbn": ["..."] } }
```

---

# Data validation

All external input must be validated.

Apply validation at:

* API requests;
* query parameters;
* file inputs, if added;
* external responses, if integrations are added.

Do not trust data from users or third parties.

Use Form Requests for writes and `$request->validated()` for persistence. Never pass
`$request->all()` to a model.

---

# Code comments

Comments must explain:

* decisions;
* reasons;
* non-obvious behavior.

Avoid comments that simply describe what the code does.

Incorrect:

```php
// Increment counter
$counter++;
```

Correct:

```php
// Keep a separate counter because the external provider may send duplicate events.
$counter++;
```

Comments are exceptional. Prefer clear names and small functions over explanatory comments.

---

# Documentation

Document:

* architectural decisions;
* complex rules;
* integrations;
* special configurations;
* assumptions that affect the API contract.

Do not document obvious code.

Keep `README.md` current: setup, credentials, endpoints, assumptions, decisions, and scaling
notes.

---

# Tests

Tests must stay close to the behavior they protect. In Laravel, use `tests/Feature` for HTTP
flows and `tests/Unit` for extracted rules.

Prioritize tests for:

* critical business logic and services;
* ownership and security;
* complex processes;
* fixed bugs.

Service tests should exercise business rules directly with in-memory SQLite and live under
`tests/Feature/Services`; pure rules belong in `tests/Unit`. HTTP feature tests protect the API
contract.

Rules:

* every business rule and fixed bug gets a test when applicable;
* tests are part of the Definition of Done;
* use `RefreshDatabase` and factories;
* do not write tests only to increase coverage.

---

# API and contracts

APIs must maintain:

* clear names;
* consistent responses;
* correct validation;
* current documentation;
* versioning under `/api/v1`.

Avoid breaking changes without planning or a new API version.

Contract rules:

* JSON only.
* Success: `data` (and `meta`/`links` for pagination).
* Errors: `message` and optional `errors`.
* `value` is a string with two decimals.
* Deletes return 200 with a JSON message.
* Foreign resources return 404.
* Pagination is 15 items per page, ordered by `created_at` desc, then `id` desc.

---

# Database

Best practices:

* use migrations;
* clear names;
* avoid unnecessarily complex queries;
* document important relationships.

Avoid:

* manual changes without a migration;
* unnecessary duplication;
* business logic inside raw queries.

Project rules:

* `isbn` is a string, max 20, digits only, not unique.
* `value` is `decimal(12,2)`, non-negative.
* Foreign keys and indexes are declared in migrations.
* Applied migrations are immutable.
* No soft deletes in the current scope.

---

# Security

Every development must consider:

* permission validation;
* protection of sensitive information;
* correct authentication handling;
* secret exposure prevention.

Never store:

* keys;
* tokens;
* credentials;

directly in code.

Project rules:

* All book routes require `auth:sanctum`.
* Every book query is scoped to the authenticated user.
* Use validated data only.
* Hash passwords; never return or log them.
* Never log tokens or sensitive payloads.
* Apply rate limits to login and the API.
* Do not expose stack traces in JSON responses.
* Use HTTPS in any non-local environment.

# Version control

## Branches

Use one branch per feature:

```text
feat/NNN-feature-name
```

Do not commit directly to the default branch without explicit approval.

## Commits

Commits must be:

* small;
* descriptive;
* related to one intention.

Use the project format:

```text
TASK-XXX: <what changed>
```

Examples:

```text
TASK-003: add book creation endpoint
TASK-005: document setup and decisions
```

Rules:

* one commit per completed task;
* do not mix unrelated refactoring with a feature;
* commit or push only when the human explicitly asks.

## Pull requests

When applicable, include:

* change description;
* reason;
* tests performed;
* special considerations.

# Dependencies

Before installing a library:

Evaluate:

* real need;
* maintenance;
* size;
* security;
* compatibility.

Avoid adding dependencies for simple problems. Sanctum, PHPUnit, and Pint are approved;
Larastan is optional. Any dependency that changes the architecture requires approval.

# Existing changes

When modifying existing code:

Prefer:

* preserving compatibility;
* incremental changes;
* avoiding unrelated refactors.

Do not rewrite working code just to match personal style.
